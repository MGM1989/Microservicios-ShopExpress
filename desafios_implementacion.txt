Bitácora de implementación — ShopExpress
Etapa 1: base ejecutable, Swagger y tablas DynamoDB
Fecha: 30/10/2026

Este archivo resume las dificultades reales de la etapa 1, para la defensa y para no repetir los mismos callejones en las etapas siguientes.


1. Spring Boot 4 y Swagger (springdoc)

El proyecto nació en Spring Boot 4.1.2 (starter webmvc, no el clásico starter-web).
springdoc 2.x (el que aparece en la mayoría de tutoriales de Boot 3) no sirve: o no arranca o Swagger da 404.

Solución: springdoc-openapi-starter-webmvc-ui 3.2.0, alineado con Boot 4.1.
Verificación: /swagger-ui.html redirige a /swagger-ui/index.html y /v3/api-docs responde 200.


2. El wrapper de Maven no era ejecutable

./mvnw devolvía "Permission denied" en WSL. El Dockerfile ya hace chmod +x, pero en el host hay que dar permiso una vez:

  chmod +x servicio-usuarios/mvnw servicio-catalogo/mvnw servicio-pedidos/mvnw


3. DynamoDB Local + AWS SDK v2: la llamada “cuelga”

El puerto 8000 estaba abierto (TCP OK) y curl al host devolvía 400 (falta de firma, esperado).
El SDK v2, en cambio, se quedaba 5 segundos y caía por timeout. No era “DynamoDB apagado”: era el cliente HTTP del SDK (Netty / checksums por defecto en 2.30) hablando mal con DynamoDB Local.

Qué se probó y no alcanzó por sí solo:
- clip-path / url() no aplica acá (eso fue el SVG del README, otra etapa)
- ApplicationRunner para crear tablas (en Boot 4 el cliente quedaba lazy si nadie lo inyectaba)
- extra_hosts + host.docker.internal
- pin de imagen amazon/dynamodb-local:2.5.4 manteniendo sqlite en disco

Qué sí funcionó:
- Cliente Apache (software.amazon.awssdk:apache-client) en lugar del HTTP client por defecto
- aws.requestChecksumCalculation / AWS_REQUEST_CHECKSUM_CALCULATION = WHEN_REQUIRED
- Inyectar DynamoDbClient en HealthController para forzar la creación del bean al arranque
- Crear las tablas dentro del @Bean dynamoDbClient(), no en un runner “invisible”


4. sqlite4java en WSL/Docker (el problema de fondo)

Con -sharedDb -dbPath /data, DynamoDB Local logueaba:

  SQLiteQueue[shared-local-instance.db]: stopped abnormally, reincarnating
  DB[...]: wasn't disposed before finalizing

En ese estado el proceso escuchaba el puerto, pero CreateTable/ListTables firmados no terminaban nunca.
Cambiar de versión 3.3.2 a 2.5.4 sin borrar el volumen reutilizaba un .db incompatible y el sqlite seguía roto.

Solución para la demo (aceptable en un trabajo de curso):

  command: ["-jar", "DynamoDBLocal.jar", "-inMemory", "-sharedDb"]

Las tablas viven en memoria. Si se reinicia el contenedor de DynamoDB, se pierden; las apps las vuelven a crear al arrancar.
No usar el volumen dynamo_data en esta etapa.


5. Dos archivos Compose y la red

docker-compose.yml (bases) + docker-compose.app.yml (apps).
docker-compose.app.yml hace include del primero para que sea el mismo proyecto y el DNS dynamodb-catalogo-usuarios:8000 funcione.
Si se levantan como proyectos distintos, el nombre de servicio no resuelve; solo el container_name.

Comando que debe usarse:

  docker compose up -d
  docker compose -f docker-compose.app.yml up --build -d


6. Orden de arranque

Usuarios y Catálogo reintentan 15 veces (2 s) si DynamoDB aún no responde. Pedidos espera el healthcheck de Mongo.
Aun así, si DynamoDB está “escuchando pero sqlite muerto”, los reintentos no sirven: hay que recrear el contenedor in-memory.


Cómo se validó la etapa 1 (estado OK)

  curl http://localhost:8081/api/health
  curl http://localhost:8082/api/health
  curl http://localhost:8083/api/health

Usuarios y Catálogo deben devolver status UP y dynamodb: [Productos, Usuarios].

  http://localhost:8081/swagger-ui.html
  http://localhost:8082/swagger-ui.html
  http://localhost:8083/swagger-ui.html

Cada Swagger muestra GET /api/health.


Lecciones para la etapa 2

- No dar por hecho que un puerto abierto = API usable (DynamoDB Local lo demostró).
- Forzar el cliente DynamoDB al startup (no dejarlo lazy).
- No volver a -dbPath/sqlite en WSL sin probar antes in-memory.
- Los CRUD de usuarios deben usar la tabla Usuarios con PK id, que ya se crea al arranque.


Etapa 3: catálogo, stock y escritura condicional
Fecha: 30/10/2026

El objetivo era dejar el inventario listo para la SAGA: alta/consulta de productos y dos operaciones atómicas (descontar y restaurar) que no permitan sobreventa.


1. Reusar el patrón que ya funcionó en usuarios

Misma receta: DynamoDbClient Apache + checksums WHEN_REQUIRED, creación de tabla Productos (PK producto_id) dentro del @Bean, y recrear la tabla si un put/get/update recibe ResourceNotFoundException (DynamoDB Local in-memory se vacía si se reinicia el contenedor de datos y las apps siguen vivas).


2. La sobreventa no se evita con un GET + PUT

Un GET de stock y luego un PUT abierto deja una ventana: dos pedidos leen stock=1 y ambos escriben 0. En DynamoDB la garantía es UpdateItem con ConditionExpression:

  attribute_exists(producto_id) AND stock >= :qty
  SET stock = stock - :qty

Si la condición falla, DynamoDB no cambia el ítem. El servicio traduce eso a 409 Stock insuficiente, o a 404 si el producto ni siquiera existe (attribute_exists). Restaurar usa solo attribute_exists y suma stock (compensación SAGA).


3. ConditionalCheckFailedException hay que mapearlo siempre

Si se recrea la tabla y se reintenta el UpdateItem, el fallo condicional del segundo intento no puede quedar sin catch (sería un 500). El repositorio envuelve ambos intentos.


4. GET vs POST y el decimal del precio

POST con precio 25.50 y GET posterior 25.5 es el tipo Number de DynamoDB: no guarda ceros a la derecha. No es pérdida de precisión para esta demo.


Cómo se validó la etapa 3 (estado OK)

  POST /api/productos prod_001 stock=2  → 201
  POST .../descontar-stock cantidad=2   → 200 stock=0
  POST .../descontar-stock cantidad=1   → 409 Stock insuficiente
  POST .../restaurar-stock cantidad=2   → 200 stock=2
  GET  /api/productos/prod_001          → 200 stock=2
  POST duplicado                        → 409
  GET  prod_no_existe                   → 404

Swagger Catálogo (http://localhost:8082/swagger-ui.html) lista Productos además de health.


Lecciones para la etapa 4

- Pedidos no debe “restar stock en Mongo”: llama a estos dos endpoints.
- El paso de reserva de stock de la SAGA es descontar-stock; la compensación es restaurar-stock.
- Un 409 de catálogo debe abortar la cadena y compensar lo ya hecho.


Etapa 4: CoR + SAGA HTTP síncrona
Fecha: 31/10/2026

Objetivo: POST /api/pedidos recorre una cadena real de handlers y, si falla después de descontar stock, restaura el inventario. GET /api/pedidos/{id} muestra estado y saga_log.


1. Spring Boot 4 cambió la URI de Mongo

spring.data.mongodb.uri ya no alimenta el cliente. El contenedor arrancaba y Tomcat escuchaba en 8083, pero MongoClient iba a localhost:27017 (dentro del contenedor no hay Mongo). /api/health se colgaba 30 s en listCollections.

Solución: spring.mongodb.uri (propiedad de Boot 4). El env SPRING_DATA_MONGODB_URI se interpola en el YAML, no hace falta renombrarlo en Compose.


2. CoR no es un comentario: si un handler lanza, no corre el siguiente

AbstractPedidoHandler llama a procesar() y solo entonces a next.handle().
Orden: ValidadorDeDatos → ValidadorDeUsuario → ValidadorDeStock → ReservarStock → ProcesadorDePago → ConfirmarPedido.
Agregar un handler no toca a los demás; se encadena en PedidoCadenaConfig.


3. SAGA envuelve la cadena

1. Persistir PROCESANDO en Mongo (documento embebido: items[] + pago).
2. Ejecutar la cadena.
3. Éxito → COMPLETADO (201).
4. Corte después de ReservarStock → POST restaurar-stock y estado COMPENSADO.
5. Corte antes de reservar (usuario 404, stock insuficiente) → COMPENSADO sin tocar Catálogo.

forzar_fallo_pago=true es el interruptor de demo del pago simulado.


4. RestClient y 404

retrieve() por defecto convierte 4xx en excepción. Los GET a Usuarios/Catálogo usan exchange() para devolver Optional vacío en 404 y no romper la cadena con un 500.


Cómo se validó la etapa 4 (estado OK)

  POST usuario usr_saga + producto prod_saga_ok stock=2
  POST /api/pedidos cantidad=1                  → 201 COMPLETADO, stock=1
  POST /api/pedidos forzar_fallo_pago=true      → 409 COMPENSADO, stock vuelve a 1
  POST usuario inexistente                      → 404 COMPENSADO (sin descontar)
  POST cantidad=99                              → 409 COMPENSADO, stock intacto
  GET  /api/pedidos/{id}                        → saga_log con cada handler

Swagger Pedidos: http://localhost:8083/swagger-ui.html
Mongo (Compass): mongodb://localhost:27017  db pedidos, colección pedidos
DynamoDB Admin: http://localhost:8001  tabla Productos (ver stock)


Lecciones para la etapa 5

- El saga_log del GET es el guion de la defensa: se ve CoR y compensación sin abrir el código.
- Postman: carpeta Feliz y carpeta Compensación con el mismo usuario/producto.
- Documentar en el README que la SAGA es HTTP síncrona (orquestación), no colas.


Etapa 5: Postman, diagramas y decisión síncrona
Fecha: 31/10/2026

No hay código de negocio nuevo. El riesgo era que el README siguiera diciendo “comunicación asíncrona” y que el docente no pudiera reproducir el flujo sin Swagger a mano.


1. Colección real, no un placeholder

ShopExpress.postman_collection.json + environment localhost.
Carpetas: 00 Health, 01 Feliz, 02 Compensación, 03 Cortes.
Feliz y Compensación crean su propio usuario/producto para no pisarse.
Tests de Postman: altas 201 o 409 (re-ejecución); pedido feliz 201 COMPLETADO; compensación 409 + stock igual.


2. Re-ejecutar Feliz agota el stock

prod_pm_feliz nace con stock 2. Cada Run folder feliz resta 1. A la tercera vez el GET previo falla (stock 0) o el POST pedido da 409. En la demo: una pasada, o restaurar stock, o cambiar la variable producto_feliz.


3. README alineado con lo que corre

- Orquestación HTTP síncrona (se eliminó “asíncrona” del diseño vigente).
- Apartado de decisión para la defensa (letra = orquestación; colas no pedidas).
- Mermaid SAGA (secuencia) y CoR (handlers).
- API Gateway marcado fuera de alcance.
- URLs de Swagger, DynamoDB Admin y Compass.


Cómo se validó la etapa 5 (estado OK)

Se reprodujo el guion de la colección contra Docker (equivalente a Run folder):

  Health x3 UP
  Feliz: 201 COMPLETADO, saga_log con 6 handlers, stock -1
  Compensación: 409 COMPENSADO, restaurado, stock igual
  Cortes: 404 usuario y 409 stock insuficiente

Importar en Postman: Collection → Import → los dos JSON de la raíz.


Lecciones para la etapa 6

- El sitio estático debe enlazar los tres Swagger y decir “el flujo completo está en Postman”.
- No embeber una consola que pegue a las APIs (CORS y otro frontend que puede fallar en la demo).


Etapa 6: sitio de defensa, seed y reset
Fecha: 31/10/2026

Objetivo: un solo URL (http://localhost:8080) para hablar y saltar a Swagger, más datos predecibles para no improvisar ids en la defensa.


1. Sitio estático, sin consola

nginx sirve HTML + Mermaid CDN. Los botones son enlaces a :8081/:8082/:8083 y Dynamo Admin :8001. Si el sitio llamara a las APIs haría falta CORS y otro frontend que puede fallar en 10 minutos.


2. Seed fijo vs Postman que “crea todo”

El guion usa usr_demo / prod_feliz (stock 5) / prod_comp (stock 2) / prod_agotado (stock 0).
reset-demo.sh reinicia Dynamo in-memory, borra la colección pedidos, espera health y POST del seed.
seed-demo.sh solo hace POST (201 o 409): no sirve para volver el stock a 5 si el producto ya existía.


3. El reset no hace --build

Reiniciar datos es rápido. Si cambió código Java hay que `docker compose -f docker-compose.app.yml up --build -d` y después el reset.


Cómo se validó la etapa 6

  ./scripts/reset-demo.sh
  GET http://localhost:8080 → 200, título ShopExpress
  GET usr_demo, prod_feliz stock 5
  POST pedido feliz → 201 COMPLETADO
  POST forzar_fallo_pago prod_comp → 409, stock 2 intacto
